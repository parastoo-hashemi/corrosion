## 1. Repository Audit Summary

The repository's scientific/implementation work is organized as **six phases**: an informal exploratory prototype (`main_first`), a benchmarked classical-ML baseline (`main`), a deep-image-embedding experiment (`main_2`), an interpretable-feature pipeline linking corrosion to structural condition and proxy-RUL (`main_3`), a robustness-diagnostic-refinement-then-refocus phase (`main_4`, itself two sub-phases: 4a diagnostic refinement, 4b terminal ultimate-load refocus), and a later, methodologically separate four-class visible-corrosion-classification/augmentation effort (`augmentation/` + `Documentation/augmentation_*`). **`out/` is not a research phase** — it is a dissemination layer of condensed IEEE-style papers that repackage main_3/main_4 results (not independent analysis, with one apparent-but-resolved exception — see §4). `Data/` and `Documentation/` hold the master workbook/images plus a large set of project-generated planning documents, and — critically — **two genuine external sources, evidence category P (predecessor/external documentation)**: an earlier MSc thesis by a different student (Al Amin Hossain, s313940) and a 2025 conference paper (ARTISTE), both describing the original physical experimental campaigns that this project builds on and partially reproduces. These are cited where they establish facts about the physical experiment (e.g. the definition of `ultimate_load_kn`, see §4/§8) but are never treated as this project's own output.

Git history is **not usable for fine-grained chronology**: the entire repo (all `main_*` generations) landed in one commit, `4ba4a65 "Add project files"` (2026-04-08), preceded only by two generic init commits. The `augmentation/` work is the only part with organic incremental commits (`f0a3253` 2026-07-06, `e1e88fb` 2026-09-10). File mtimes are more informative but must be used cautiously: a cluster of files across *every* generation (`main_first`, `main`, `main_2`, `main_3`, `main_4`, `main_4_old`) share the identical modification timestamp 2026-04-01 16:58. **Historically**, the pipeline's configuration files held valid numeric values — this is evidenced by successful, dated output artifacts that could only have been produced with working numeric config (e.g. `main_4/outputs/features/image_features.csv`, dated 2026-03-16; `run_ultimate_load_refocus.log`, dated 2026-03-25). **Currently**, four YAML config files in `main_4`/`main_4_old` contain a corruption: every literal numeral `1` inside a YAML value has been replaced with the string `main_first` (e.g. `reg_lambda: 1.0` → `reg_lambda: main_first.0`), which would break re-execution of the affected code paths today. The repo's squashed git history contains no pre-corruption diff, so the **mechanism is inferred, not proven**: the coincidence in timing with the cross-generation 2026-04-01 16:58 touch is circumstantial, consistent with (but not proof of) a single automated bulk text-replacement operation. This is treated strictly as a Software-Engineering/Reproducibility finding (§ Ch.7) and flagged as an open question in §8 — it is not used as evidence for any scientific conclusion.

Dataset-size handling differs by generation, and the difference is a genuine methodological choice rather than a simple discrepancy (verified directly against each generation's loading code and saved run artifacts — see §4 item 2 for full detail): **`main`, `main_2`, and `main_3` each retain all 792 image-linked rows**, encountering the one corrupted, unreadable image (`E01-20240508-17W.png`) only at the feature/embedding-extraction step and imputing its missing values with the per-column median (verified in `main/image_features.py`, `main_2/data.py`, `main_3/src/features/extractor.py`). **`main_4` instead applies an explicit data-quality policy** (`configs/dataset.yaml: data_policy.use_only_aligned_readable_images: true`) that excludes any image it cannot align to a readable, usable row, yielding **791 aligned rows** from **792 image files** (`main_4/outputs/audit/verified_facts.json`); the later `augmentation/` effort inherits main_4's 791-row exclusion convention. In all cases there are **48 unique specimens**, of which only the **48 terminal-stage rows** carry structural labels (`wire_area_loss_frac`, `ultimate_load_kn`) — one per specimen.

The scientific arc **is** evidence-supported, with important corrections to the brief's proposed story (see §7): main_3 already implemented GroupShuffleSplit/LOTO/LOCO and already *named* campaign confounding and metadata-shortcut learning in its own report — main_4 did not discover these problems, it **quantified and acted on** problems main_3 had already flagged (a nuance the final report must get right). The single strongest, most defensible finding in the whole project is main_4's ultimate-load-refocus mesh-stratification result: a pooled corrosion-vs-load correlation (Spearman ρ=0.462, p≈0.001) **weakens or reverses** once stratified by steel-mesh family (mesh_4: ρ=−0.046; mesh_7: ρ=−0.40) — evidence of substantial confounding by specimen-group structure that prevents the pooled correlation from being read as a direct corrosion-capacity relationship, and the closest thing the project has to a decisive negative-result-turned-insight. This finding concerns the **structural** endpoint specifically; the **visible-corrosion** stage, by contrast, remains robust under the same leave-one-campaign-out evaluation (Spearman ≥0.97 for both surface targets, see §4/§7) — the collapse is specific to hidden structural condition, not a general failure of campaign generalization.

## 3. Project Evolution Timeline

Presented as a scientific sequence, cross-checked against code/config/report content rather than folder names or raw mtimes alone (mtimes are corroborating, not primary, given the bulk-import git history). Phase numbering matches §2.

1. **Phase 0 — Original exploratory scripts (`main_first`).** A brief, informal prototype that establishes the starting point and motivation for the benchmarked pipeline, nothing more: can week-to-week rust percentage and a naive RUL be estimated from images using an off-the-shelf color mask and RandomForest? It produced a working demo (autoregressive RUL simulation) with no held-out evaluation for its "production" model and hand-tuned, string-parsed features, no principled feature engineering, and no persisted metrics — motivating the move to a benchmarked, evaluable pipeline with genuine feature engineering (Phase 1).

2. **Phase 1 — Classical-ML baseline (`main`).** *Research question:* can a benchmarked, leakage-aware classical-ML pipeline predict current corrosion, progression, and time-to-threshold from proper handcrafted features + metadata? *Result:* RandomForest/GradientBoosting selected per task; strong headline R² (0.90 for current corrosion) but self-diagnosed as largely a restatement of the rust-mask threshold (91.5% feature importance from one color-mask feature). *Limitation discovered (explicit in `1_main.pdf` §11-12):* three tasks with three different scientific meanings; sparse structural endpoints (48 rows) left unmodeled; test-set-driven model selection; no image-based signal in 2 of 3 tasks. *Why the next phase started:* to test whether deep image representations could add real, non-tautological signal, and to start addressing the unmodeled structural endpoints.

3. **Phase 2 — Deep image embeddings (`main_2`).** *Research question:* do frozen deep embeddings (ResNet-18/ImageNet) outperform handcrafted features for corrosion quantification, alone or fused with metadata? *Result:* **negative for fusion** — the image-only MLP beat the multimodal (image+metadata) MLP on the held-out test fold, despite multimodal being better on validation; documented as a named "negative result" in the project's own report. Structural/RUL targets still untouched. *Limitation discovered:* small effective test set (10 specimens after grouped split), late-stage under-prediction, test-set model selection recurs, unclipped predictions can go physically negative. *Why the next phase started:* the project's own future-work section explicitly recommends reintroducing interpretable RGB-threshold features and comparing them against deep embeddings — this is the direct, code-documented seed of Phase 3's interpretable-feature approach.

4. **Phase 3 — Interpretable corrosion → structural condition → proxy-RUL (`main_3`).** *Research question:* using genuinely interpretable, multi-family handcrafted features (91 features: color/HSV/Lab, GLCM/LBP texture, morphology, spatial/strip-position) and specimen-grouped, treatment-grouped, and campaign-grouped splits, can visible corrosion be linked to hidden structural condition and a proxy-RUL? *Result:* surface corrosion regression works well in-distribution (MAE 1.38 for total rust); hidden-damage regression is weak (`wire_area_loss_pct` R²=0.31, `ultimate_load_kn` R²=0.385, RandomForest MAE 0.121 kN on this generation's own 38/10 grouped-holdout split) and **already visibly unstable under LOTO** (R² swinging from +0.76 to −50.75 across treatment folds); the project's own report already names campaign confounding and a "downstream label shortcut" (manual corrosion labels used as damage-model inputs) as concrete technical risks; correlation between visible corrosion and wire loss is near-zero (r=0.021). Proxy-RUL is computed and consistently never mislabeled as true RUL. *Limitation discovered (explicit, in the project's own words):* "Small structural supervision… is the dominant bottleneck"; hidden-damage predictions used to build degradation curves are in-sample fits, not held-out evidence. *Why the next phase started:* main_3 itself specifies almost the entire main_4 agenda in writing (ablations isolating metadata vs. image signal, out-of-fold estimates, monotonic degradation constraints) — main_4 operationalizes fixes for problems main_3 already named, rather than discovering new ones.

5. **Phase 4a — Robustness and diagnostic refinement (`main_4`, first half).** *Research question:* how badly do hidden-damage models degrade under genuine distribution shift (leave-one-campaign-out), and what drives that degradation? *Result:* quantified collapse for the structural targets — `ultimate_load_kn` MAE inflates 3.24× (0.174→0.564 kN, this generation's own group_shuffle-vs-LOCO comparison) under LOCO; `wire_area_loss_frac` grouped Spearman only 0.280, collapsing to −0.089 under LOCO; feature-redundancy audit finds 36 high-collinearity pairs and near-tautological feature/label pairs; metadata-only feature sets are consistently the most robust for the structural targets, implicating exposure/treatment-design metadata (not images) as the dominant robust signal. By contrast, the **surface/visible-corrosion targets do not show this collapse**: `surface_total_rust_pct` and `peak_rust_pct` retain Spearman ≥0.97 under the same leave-one-campaign-out evaluation (`outputs/diagnostics/tables/benchmark_best_model_robustness.csv`) — the generalization failure is specific to hidden structural condition, not a property of the pipeline as a whole. *Limitation discovered:* campaign is confounded with mesh count, NaCl level, and exposure duration for the structural subset — pooled cross-campaign generalization of structural predictions is fundamentally limited by experimental design, not fixable by more modeling. *Why the next phase started:* the confound is structural (mesh/campaign co-linear), motivating a redesign of the research question itself around a directly measured, terminal, non-time-series endpoint.

6. **Phase 4b — Terminal ultimate-load refocus (`main_4`, second half).** *Research question (explicit, from config/README):* "After controlling for specimen design, does superficial corrosion add predictive value for terminal ultimate load?" *Result:* metadata-only Ridge is the best and most robust model (MAE 0.173 kN, Spearman 0.758); adding RGB/HSV image descriptors yields no meaningful improvement pooled, and the pooled corrosion-vs-load correlation (ρ=0.462) **weakens or reverses once stratified by mesh family** (mesh_4: ρ=−0.046; mesh_7: ρ=−0.40) — evidence of substantial confounding by specimen-group structure that prevents the pooled correlation from being read as evidence of a direct corrosion-capacity relationship (not proof that no such relationship could exist under other conditions). *Limitation discovered:* under LOCO, all feature sets still collapse (best MAE 0.465 kN vs. 0.173 baseline) — refocusing the target did not remove the campaign-extrapolation problem, only made the in-distribution finding more defensible. *Status:* the legacy hidden-damage/degradation/proxy-RUL pipeline is retained for traceability but explicitly demoted to non-preferred in the current `README.md`.

*(Dissemination, not a research phase)* — `out/` repackages main_3's and main_4's already-saved results into IEEE-conference format for external communication. One number initially flagged as a possible mismatch (`corrosion_condition_pipeline_ieee.pdf`'s "0.121 kN" ultimate-load MAE) was traced directly to main_3's own `damage_regression_metrics.csv` (RandomForest, group_shuffle split, n=38/10: MAE=0.1207) — it is main_3's own valid, version-specific result, not an error or a mismatch against main_4 (which used a different pipeline, feature set, and split composition to obtain 0.174 kN). See §4.

7. **Phase 5 — Four-class corrosion classification + augmentation (`augmentation/`, later/separate).** *Research question:* can a robust, class-imbalance-aware, augmentation-supported classifier be built for four-class visible-corrosion severity (`A_Total_Rust_Category_1-4`), using an augmentation methodology tailored to a position/color-tolerant classification target (unlike main_4's position-sensitive regression features)? *Status (2026-07 to 2026-09, the most recent work in the repository):* dataset preparation, leakage-safe train/val/test splitting (train-only augmentation enforced by a runtime assertion), and five augmentation recipes are complete; **no classifier has been trained** — explicitly deferred to a "planned journal paper." Class imbalance (658/99/20/14 images across classes 1-4) is documented as unaddressed and left as a requirement for the not-yet-written training script.

## 4. Contradiction / Version-Change Register

**Note on an apparent discrepancy that did not survive verification:** an earlier draft of this register listed a mismatch between `out/corrosion_condition_pipeline_ieee.pdf`'s "0.121 kN" ultimate-load MAE and main_4's saved "0.174 kN." Direct verification shows these are **not in conflict**: the paper (sourced from `main_3/reports/corrosion_condition_pipeline_ieee.tex`, §"Hidden-Damage Modeling") explicitly and correctly reports **main_3's own** grouped-holdout result — confirmed byte-for-byte against `main_3/outputs/damage_regression_metrics.csv` (`group_shuffle,fold_00,mixed_specimens,random_forest,ultimate_load_kn,...,38,10,0.12068...`, i.e. n_train=38/n_test=10). Main_4's 0.174 kN comes from a different generation's pipeline (different feature engineering, different code, a different — though also nominally "group_shuffle" — train/test fold composition, and an N=791 vs. main_3's N=792 basis). Both numbers are genuine, valid, version-specific historical results for the same target from two different implementations; neither is stale or in error. This is **not listed as a contradiction below** — it is recorded here only so the resolution is not lost.

## 7. Central Project Narrative

This project began as an attempt to predict a ferrocement specimen's visible corrosion state and its relationship to internal structural condition directly from time-series surface photographs, progressing from a brief, informal single-algorithm prototype (`main_first`) through an increasingly rigorous classical-ML baseline (`main`) and a deep-embedding experiment (`main_2`) to a structured, interpretable pipeline (`main_3`) that explicitly attempted to connect visible corrosion to hidden structural condition and a proxy remaining-useful-life. At every phase after the first, the project's own generated reports were unusually candid about the resulting weaknesses: `main`'s handcrafted-feature model was shown to be substantially a restatement of the very color threshold used to compute its own label; `main_2`'s deep-embedding fusion underperformed a simpler image-only model on held-out data; and `main_3`, while already implementing rigorous specimen-grouped, treatment-grouped, and campaign-grouped evaluation, found that hidden-damage prediction was unstable to the point of negative R² under leave-one-treatment-out, and explicitly named the two root causes in writing: only 48 terminal-stage structural measurements exist across the entire dataset (one per specimen, with no repeated structural sampling), and the experimental campaigns are themselves confounded — steel-mesh count, NaCl concentration, and exposure duration co-vary with campaign, so a model trained within one campaign extrapolates, rather than genuinely generalizes, when applied to the other.

`main_4` took these self-diagnosed weaknesses and quantified them rigorously, and the quantification revealed something specific: it is the **structural** targets (`wire_area_loss_frac`, `ultimate_load_kn`) that collapse under leave-one-campaign-out evaluation — ultimate-load MAE inflated 3.24× relative to a standard grouped holdout — while the **visible-corrosion** targets (`surface_total_rust_pct`, `peak_rust_pct`) retain Spearman correlations at or above 0.97 under the same campaign-holdout evaluation. Feature-importance and robustness analysis further showed that whatever robust structural signal existed came predominantly from experimental-design metadata (mesh count, treatment, NaCl level) rather than from the corrosion images. Rather than treating the structural collapse as a modeling problem to be engineered around, the project made a defensible scientific decision to refocus: instead of trying to predict a sparse, campaign-confounded hidden-damage proxy or an unreachable "true" remaining-useful-life, it re-targeted the one directly measured, physically meaningful terminal endpoint available — the terminal ultimate load recorded at the end of each specimen's aging period (defined, per the predecessor thesis, as the peak load recorded during a four-point bending test) — and explicitly tested, rather than assumed, whether visible corrosion adds predictive value once specimen design is controlled for. The resulting analysis is the project's most scientifically informative finding: a pooled correlation between visible corrosion and terminal ultimate load that looks statistically real (ρ=0.462) weakens or reverses once the data is stratified by steel-mesh family (mesh_4: ρ=−0.046; mesh_7: ρ=−0.40). This indicates substantial confounding by specimen-group structure and prevents the pooled correlation from being interpreted as evidence of a direct corrosion-capacity relationship — it does not, on its own, prove the pooled relationship is purely an artifact with no underlying corrosion effect, only that the pooled evidence cannot support such a claim. This is precisely the failure mode the project had been warning about in its own documentation since main_3.

The strongest current, evidence-backed conclusions are therefore modest but genuine, and depend on which endpoint is being discussed: (1) visible surface corrosion can be quantified from images with good in-distribution accuracy, and this accuracy is largely retained under campaign-holdout evaluation — the visible-corrosion stage is the project's most robust result; (2) prediction of hidden structural condition (wire-area loss, terminal ultimate load) from the same images is comparatively weak and collapses under campaign-holdout evaluation specifically, with metadata describing specimen design proving a more robust — though scientifically less interesting — predictor of terminal structural condition than anything derived from the corrosion images; and (3) any claim that visible corrosion predicts hidden structural loss or remaining service life must be qualified by the sparse, single-terminal-measurement, campaign-confounded nature of the available structural ground truth. Two matters remain open rather than concluded: a separate, later-started effort to build a robust four-class visible-corrosion-severity classifier has completed careful, leakage-safe data preparation and a tailored augmentation methodology but has not yet trained or evaluated a classification model (explicitly deferred to a planned future paper); and the repository currently contains a reproducibility defect in several `main_4` configuration files (numeric values replaced by a text string, cause unproven) that would need to be repaired before the refocus pipeline's exact numbers could be regenerated from scratch — a software-engineering caveat about re-running the pipeline today, not a challenge to the validity of the previously generated outputs and reports, which remain valid evidence of what was found.
